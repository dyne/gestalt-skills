# Decide who signs before scheduling a release

Ask the release owner whether customer downloads must carry a trusted publisher signature and which existing identity and signing integration are approved. Search for `sign-exe`, SignTool, timestamp settings, `SignedUninstaller`, managed actions and protected release environments. Record the expected signer and trust policy. If trusted signing is required and the certificate profile or CI authorization is missing, **block publication**, name the missing access and continue unsigned fixture verification. For an intentionally unsigned release record that decision before publishing and disclose it to users.

`AppPublisher`, PE `CompanyName` and the icon are editable product metadata. Authenticode binds the bytes to a signer through a certificate chain. SmartScreen also evaluates reputation; a valid signature alone cannot guarantee a warning-free launch. [Microsoft's Windows code signing guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)

1. Build, stamp and stage project-owned PE files. Sign each through the existing signing command or managed service, using SHA-256 and an RFC 3161 SHA-256 timestamp. Verify each signature and the expected publisher before ISCC embeds those files. Preserve third-party signatures.
2. If the uninstaller must be signed, configure Inno's named `SignTool` with `SignedUninstaller=yes`. Supply its command through the compiler's `/S<name>=...` option on the protected signing runner. The wrapper must pass the quoted Inno `$f` filename through to the same signer and propagate exit status. Inno can sign both its generated uninstaller and Setup on this path. Inspect the installed uninstaller too. [Inno signing directives at the pinned version](https://github.com/jrsoftware/issrc/tree/is-6_4_3/ISHelp)
3. Sign the completed Setup EXE if ISCC has not already signed it. Verify the **final** EXE. For a public Windows release use `signtool verify /pa /all /v /tw setup.exe` and fail on a nonzero status, including a missing-timestamp warning. Check the expected signer identity as well as chain validity. Use the project's certificate policy for subject changes or rotations. A test certificate validates the fixture plumbing only.
4. Generate the verification receipt, public checksums and WinGet hashes after the last signature or timestamp is added. Smoke-install those bytes and send them unchanged to publication. On download, recompute the checksum and verify the Authenticode signature again. [SignTool options](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)

**Azure Artifact Signing example.** Establish public-trust eligibility and complete identity validation for the relevant organization or individual. Obtain an Azure subscription, resource group, signing account, its region-specific endpoint and certificate profile name. Assign the CI principal the **Artifact Signing Certificate Profile Signer** role at the required profile scope (older tooling uses “Trusted Signing”). Link the GitHub repository's protected release environment or exact release ref to the Entra application or user-assigned identity through a federated credential. Match its issuer, subject and audience. The signing job requests `id-token: write` and `contents: read`, then uses `azure/login` with the tenant, subscription and client identifiers. Invoke the maintained signing action or SignTool provider using the endpoint, account, profile and timestamp service. Pin the reviewed action revisions. Use normal read-only jobs for PR fixtures. Never request a private key, PFX, password, token or credential dump in chat, logs or project metadata.
